# Чат и агенты — требования к LLM-оркестратору

В прототипе ответы — заготовки и правила на регулярках (`chatReply`, `psParse`, `pkSend`, `routeIntent`, `ikParse`). Ниже — что из этого должно стать оркестратором. Всё, что про устройство оркестратора, — **предложение**; поведение и тексты — из прототипа.

## 1. Где живут чаты

| Чат | Что это | Данные | Прототип |
|---|---|---|---|
| Общий чат кабинета (колонка, «док») | Колонка между меню и экраном, работает на любом экране. При входе закрыта, кнопка «Чат» подсвечена. На «Чатах» колонка скрыта — страница сама чат | `CHATS` id `dk`; клиент чата = текущий клиент, при смене — системная строка «Клиент — …» | `DOCK`, `dockRender`, `dockSend`, `dockChat` |
| Чаты (список) | Разговоры с Maker по темам; «Без клиента» допустим; контекст «Знает о «Клиент»: стиль и тон, сайт… · Изменить» | `CHATS[]`: `p`, `ctx[]` из `CTX_ALL` (Стиль и тон, Сайт, Страницы, Кампании и результаты), `cost` | `renderChat`, `chatSend`, `chSync` |
| Главная | Поле задачи (текст, голос, файлы, ссылки) → отправляет в общий чат, пользователь остаётся на месте | — | `hcSend` (обёртка) |
| Чат поста | Слева разговор о посте, справа пост с версиями. В колонке, если она открыта | `SOC.chat[]`, `SOC.vers[]` | `psRender`, `psSend`, `psParse`, `dockAdopt` |
| Чат стартового набора | Разговор со всем клиентом; справа — карточки набора | `PK.chat[]` | `pkSend`, `pkRender` |
| Сценарий создания (DCR) | Временный разговор в колонке до запуска; после — итог в общий чат | `DCR {v, msgs, text, draft, edit}`, не хранится | `dcrStart` … `dcrCommit` |

**(предложение)** Хранить все чаты как одну сущность `Chat` с `kind ∈ cabinet | topic | publication | starter_kit` и ссылкой на объект. Сценарий создания — не чат, а черновик операции создания (`CreationDraft`) с полями окна. Общий чат: один на пользователя или кабинет? — open-questions.

## 2. Агенты-персонажи

| Ключ | Имя | Роль | Отвечает за | Экраны по умолчанию (`DK_AG_V`) |
|---|---|---|---|---|
| `Maker` | Мика | координатор | общий помощник, маршрутизация, «что сделать сегодня», стартовый набор | Главная, Чаты, профиль, всё прочее |
| `Стратег` | Тим | стратег | цели, аудитории, рубрики | `strat` |
| `Контент` | Ася | контент-редактор | план, посты, карусели, сторис, клипы, страницы, презентации, фото и видео, шаблоны, ответы во входящих | `plan images video pages pres deck templates soc-* inbox` |
| `Реклама` | Лев | специалист по рекламе | баннеры, кампании, цифры, аудитории для рекламы | `banners campaigns camp result groups` |
| `Бренд` | Нора | бренд-менеджер | стиль, голос, факты | `style voice facts` |

**Выбор агента:** `DOCK.ag = 'auto'` → по текущему экрану (`DK_AG_V[ROUTE.v]`, иначе Мика); вручную — меню «Спросить: … ▾» («Сам решит / Тим / Ася / Лев / Нора»). Персонажи — только оформление (рисованный аватар, имя, должность; выключаются в профиле и в меню — тогда всё подписано «Maker»). **Роль агента при этом остаётся** — она определяет системный промпт и набор инструментов.

**Требования:**
- R1. Агент — это профиль: системный промпт, разрешённые инструменты, приоритетные данные клиента. Не отдельные модели.
- R2. Мика решает, какому агенту передать, если `auto` и экран не определяет задачу (например, на Главной «сделай баннеры» → Лев/раздел баннеров).
- R3. У каждого ответа — поле `agent`, чтобы подписать сообщение (`m.ag`).

## 3. Что делает чат с сообщением (порядок)

Общий чат (`dockSend` + обёртки):
1. **Маршрутизация** (`routeIntent`): глагол действия (собери, сделай, создай, напиши, сними, подготовь, сгенерируй, нарисуй, запусти, нужен, составь) + предмет (пост, карусель, сторис, клип/reels/шортс, баннер/креатив, лендинг/страница/сайт, презентация/колода/отчёт, ролик/видео, фото/кадр/картинка, контент-план, стратегия, кампания/рекламу, аудитория, факт) → ответ «Это делается в «Раздел» — перехожу и начинаю там» → переход: «Посты» — их чат с вписанной темой (без списания, отправляет человек); остальные — сценарий создания сразу с карточкой «Сделаю так». С вложениями — не маршрутизируем. Вопросы без глагола («как дела у рекламы?») — обычный ответ.
2. **«Что сделать сегодня»** → топ-3 напоминания со ссылками (`TD_LIST`).
3. **«Чего не хватает»** → пропуски клиента (`faGaps`) + пробелы для стратегии (`ikGaps`) + ссылка в «Базу фактов». Без клиента — «выберите клиента».
4. **Новый пользователь** + «пакет / набор / бриф» или текст >220 знаков → предложение собрать стартовый набор.
5. **Нет клиента** → «Поняла задачу. Для кого делаем?» с кнопками клиентов, «+ Новый клиент», «Ответь в общем» (бесплатно; ответ после выбора).
6. Иначе — **ответ ассистента** (0,82 ₽), с действиями под ответом и кнопкой «Собрать в «Раздел»» (если на экране есть создание).

Требование R4: маршрутизацию и классификацию намерений делает оркестратор (дешёвая модель или правила), а не прототипные регулярки; результат — структурированный `intent` (см. §6), фронт переходит по нему.

## 4. Уточняющие вопросы вместо пропусков (`CHQ`)

Если в ответе есть неизвестное, ответ **не показываем с оранжевыми полями**: ассистент спрашивает по одному, как в Claude.
- Карточка `.chq`: «1 из N», вопрос, варианты, **первым — подходящий факт «из базы фактов»**, «Свой вариант», «Пропустить», «← Назад». Сообщение в поле ввода тоже считается ответом.
- После всех ответов — финальный текст, где ответы вставлены жирным (вариант посреди фразы — со строчной), пропущенное — серым курсивом.
- Ответы-факты (`CHQ[метка][2] = 1`: скидка, цена, оффер, акция, отличие, факт или цифра) сохраняются в базу фактов клиента.
- Словарь меток (`CHQ`): `[ваша скидка]` → «Какую скидку даёте?» (10% / 15% / 20%), `[сумма в день]`, `[имя]`, `[причина задержки]`, `[что изменили]`, `[имя администратора]`, `[что случилось и что сделали]`, `[ваш оффер]`, `[цена]`, `[акция или новинка]`, `[чем вы отличаетесь — одной фразой]`, `[кому продаём]`, `[сколько заявок или продаж]`, `[ваша услуга]`, `[ваша акция]`, `[что делаете]`, `[факт или цифра из базы]`, `[главная мысль поста]`. Нет метки — «Уточните: …?».

Требования:
- R5. Модель возвращает текст **с каноническими метками пропусков** и отдельный список `questions[]` (метка, вопрос, варианты, `is_fact`). Новая метка = новая запись словаря (храним на сервере, не в коде фронта).
- R6. Перед вопросом оркестратор ищет ответ в базе фактов клиента и предлагает его первым.
- R7. Финальная сборка ответа после вопросов — без повторного списания **(предложение)**.

## 5. Сценарий создания (DCR) и карточка «Сделаю так»

Разделы: страницы, фото, видео, баннеры, кампании, аудитории, факты, стратегия, план, карусели, сторис, клипы, презентации (`DCR_ON`). У постов — свой чат.

1. Приветствие одной строкой (`DCR_TXT[v].hi`): «Новая страница для «Вита» — о чём она?», «Расскажите о «Вита»: что продаёт, кому, чего хотим от соцсетей.» и т. д. Без клиента — «Для какого клиента?». В стратегии и плане — подсказка пути (`cpHint`: нет стратегии / стратегия дополнится; в плане — учёт результатов публикаций).
2. Над полем — лента чипов: 3 ближайшие темы плана (для страниц и баннеров тема превращается в текст задачи), «Темы из плана ждут сборки · N» (публикации), шаблоны/стартеры, «Показать на примере».
3. Текст → карточка «Сделаю так:» (+ «остальное — из базы фактов, пропуски спрошу после», если текст <40 знаков). Поля — **те же, что в окне создания раздела** (`dcrCtl`): выпадашки → чипы, переключатели → галочки, площадки/форматы → мультивыбор, кнопки вроде «Первый кадр: выбрать». «Ещё настройки» не показываем. Дописать текст — «Добавила.», «Изменить текст» — «Обновила.».
4. «Создать» → ворота денег → `dcrCommit`: в общий чат пишется задача и «Собираю страницу для «Вита»: цель — запись, иллюстрации бренда…», результат справа.

Поля окон создания (для схемы `CreationDraft`):

| Раздел | Поля |
|---|---|
| Страница | цель (Заявки/Звонки/Запись/Продажа), иллюстрации бренда, версии под аудитории |
| Кадры | что снимаем (люди и сцены / продукт крупно / абстракции), формат (1:1, 16:9, 9:16, 4:5), кадров 1/4/8; доп.: качество, сюжеты придумывает Maker |
| Ролик | первый кадр*, как снимаем (быстрее и дешевле / реалистичнее / плавнее), 5/10/15 с, форматы 9:16 1:1 16:9 |
| Баннеры | фон (светлый фон бренда / кадр клиента), цель |
| Кампания | предложить состав из готового |
| Стратегия | период 1/3/6/12 |
| План | период, тем в месяц 8/12/16 |
| Пост / карусель / сторис / клип | площадки; слайдов 5/7/10; кадров 3/4/6; длительность 15/30/60 |
| Презентация | тип, слайдов 8/12/16 |
| Аудитории, факты | только текст |

R8. Сервер отдаёт описание полей раздела (`GET /creation-forms/{section}` — **предложение**), чтобы карточка и окно строились из одного источника; модель может предзаполнить поля из текста (`fields_suggested`).

## 6. Вход и выход модели

### Контекст на вход (собирает оркестратор, не фронт)

| Блок | Источник | Когда |
|---|---|---|
| Клиент: название, ниша, сайт | Client | всегда, если клиент выбран |
| Голос: `tone.formal/emo`, «так говорим / не говорим», источники голоса | Style, VoiceSource | любые тексты |
| Стиль: цвета, шрифты, манера фото, эталоны | Style | кадры, баннеры, страницы, слайды |
| Факты по категориям, **запреты** | Fact | всегда; запреты — жёстко |
| Аудитории | Audience | стратегия, тексты, реклама |
| Стратегия: цель, позиционирование, мысли, рубрики, площадки | Strategy | план, публикации, страницы, отчёты |
| Тема плана: мысль, факты, рубрика | PlanItem | сборка из темы |
| Правила площадок | `SOC_FMT` | публикации |
| Экран и открытый материал | `ROUTE.v`, `dockWhere()` | общий чат |
| Переключатели контекста чата | `Chat.ctx` | «Чаты» (выключено всё — «отвечаю в общем») |
| Вложения: файлы, картинки, ссылки | uploads | если есть |
| История разговора | messages | чаты |
| Цифры: кампании, результаты публикаций | Campaign, CampaignDay, PostStat | реклама, отчёты, «Дать больше тем» |

### Ответ модели — структура, а не только текст

```json
{
  "agent": "Контент",
  "intent": {"type": "answer|route|ask_client|starter_kit|create", "section": "banners", "prefill": {"text": "...", "fields": {"goal": "Запись"}}},
  "text": "Черновик в тоне клиники: … [причина задержки] …",
  "placeholders": ["[причина задержки]", "[что изменили]"],
  "questions": [{"label": "причина задержки", "q": "Почему в тот день задержались?", "options": ["…"], "is_fact": false}],
  "actions": ["post", "banners", "page", "plan", "shot"],
  "facts_used": ["f2", "f3"],
  "facts_to_save": [{"cat": "Цены и условия", "t": "…"}],
  "entities": [{"type": "publication", "id": "s51", "status": "draft"}],
  "basis": ["голос", "тема плана", "3 факта"]
}
```
`basis` хранится для аудита, но в UI строку «Опираемся на…» **не показываем** (решение 8 окт).

### Генераторы и их структурированный результат

| Задача | Выход | Прототип |
|---|---|---|
| Разбор рассказа | `{groups[{n,who,task,geo,age,obj}], facts[{cat,t}], voice{formal±, emo±, say[], lab[]}, goal, goalN, goalRev, pos, msgs[], ch[], links[], left[]}` | `ikParse` |
| Стратегия | поля Strategy, рубрики с долями = 100 | `strCreate` |
| План | названия тем по рубрикам/датам (распределение — алгоритмом), мысль, факты | `plCreate`, `plBank` |
| Пост | текст под каждую площадку в рамках лимитов и правил хэштегов | `socGen`, `plSocFrom` |
| Правка поста | новый текст + `version_note` («короче», «+ Telegram»…), стоимость по типу правки | `psParse` |
| Карусель / сторис / клип | `slides[{h,s}]` / `frames[{h,s,img,stk}]` / `scenes[{t,d}]` | `socSlides`, `socFrames`, `socScenes` |
| Баннеры | 3 × `{h ≤48, s ≤80, c}`, кнопка по цели (`CTA`) | `bnCreate` |
| Страница | блоки по шаблону с фактами, пропуски | `pgContent` |
| Колода | outline `[{l,h,b[]}]`, затем слайды + заметки докладчику | `dkCreate`, `dkBuild`, `OUTLINES` |
| Отчёт за месяц | слайды из цифр (цифры считает код, модель — выводы) | `repBuild` |
| Кампания | `{v, type, to, groups[], ch}` | `parseAsk` |
| Ответ во входящих / на отзыв | текст в голосе, по оценке, `[пропуски]` | `ibDraft` |
| Голос словами | сдвиги ползунков + правила | `voAsk` |
| Кадр/ролик | промпт для генератора из стиля и манеры фото | `ipGen`, `vdCreate` |

## 7. Требования к оркестратору (сводно)

- R9. **Не выдумывать.** Цены, адреса, цифры, имена, сроки, условия акций — только из фактов или ответов; иначе каноническая плашка. Запреты клиента («не пишем «лучшие врачи»») — жёсткий фильтр, проверка выхода.
- R10. **Голос** клиента — в каждом тексте; «так не говорим» — проверка выхода.
- R11. **Структурированный выход** по JSON-схеме; невалидный — повтор, не показ пользователю.
- R12. **Стриминг** текста ответа в SSE (`chat.delta`), «печатает…» — один раз (не дублировать при агенте и typing).
- R13. **Деньги:** оркестратор не списывает сам — сообщает стоимость шага; списание через ворота (холд/списание). В стартовом наборе — списание за каждый шаг.
- R14. **Сущности** создаются только через доменные сервисы (те же, что у REST), черновиками. Ответ возвращает их id и ссылку «Открыть в …».
- R15. **Без моделей в UI:** пользователь выбирает «быстрее/лучше», режим маппится на провайдера на сервере (`VD_MODE`, `SERIES.model` — внутреннее).
- R16. **Непонятое** — честный список того, что умеем в этом месте (как `psParse` п. 9), а не догадка.
- R17. **Конфликт данных** (цена в брифе ≠ в базе) — спросить, не выбирать самим (`pkConflicts`).
- R18. **Короткий текст задачи** — собрать по базе фактов, пропуски спросить после, не блокировать.
- R19. **Память клиента, а не чата:** в стартовом наборе и сценариях агенты берут данные из базы клиента, куда сначала разложен бриф, а не из сырого текста разговора.
- R20. **Логи:** запрос, контекст (id фактов), ответ, стоимость, агент — для разбора жалоб «откуда цифра».
